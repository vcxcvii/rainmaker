# Decisions

## 2026-07-29

- GSC snapshots end three UTC days before collection. Search Console data can lag, so this keeps every rolling 28-day comparison complete.
- GA4 Data API page reports expose page-level `keyEvents`, not arbitrary ordered page sequences preceding an event. `conversion_paths` and `paths_sampled` remain `0`; conversion-path tiering stays disabled instead of presenting direct event counts as paths.
- An active GA4 key event means the event returned a non-zero `keyEvents` value inside the selected window. A configured event with no activity cannot be discovered through the Data API alone.

## 2026-07-30

- `context_hash` covers the body of `context/business.md`, not the frontmatter. The frontmatter carries `strategy_version`, which every strategy write bumps, so hashing the whole file would make each write invalidate its own hash and the drift check would fire constantly on nothing. The body is trimmed at both ends before hashing, because rendering adds a blank line after the frontmatter.
- `context --sync` accepts the prose as authoritative by rehashing and bumping the version. It does not parse the edited prose back into records. Saying so in the output is deliberate: silently implying that hand-edited paragraphs became typed records would be worse than the gap itself.
- Field ownership is matched by longest dotted-path prefix, with a collapse rule so `pain_points.pp3.status` resolves to the `pain_points.status` owner rather than the `pain_points` owner. Without the collapse, per-record paths would always fall back to the coarsest rule and shared fields could not exist.
- Every ownership-legal change still requires a `decisions` entry covering its path. A strategy that changes without a recorded reason cannot be argued with three months later, which is the whole point of keeping it.
- The metric definitions live at `skills/_shared/metric-definitions.md`, not at `skills/explain-this-number/references/definitions.md` as v1 specified. Every skill cites them, so a copy owned by one skill would drift from the copy everyone else reads. The skill points at the shared file and holds no definitions of its own.
- Block 7's acceptance criteria are a test rather than a review step. `src/skills/shared.test.ts` fails the build when a required term is missing, when a definition loses its misuse or replacement line, when a skill omits the shared context-load block verbatim, or when a skill restates shared reference content instead of citing it.
- Query intent classification is one implementation, `src/analyze/intent.ts`, shared by tiering rule 5 and the SERP verdict engine. It previously existed only inline inside `tiering.ts`; factoring it out is what spec/false-positives.md section 5 requires: the same detection logic in two places is how thresholds drift and two reports contradict each other.
- SERP page-format classification (`classifyFormat`) is a keyword heuristic in the style of `tiering.ts`'s URL patterns, not NLP. It is deliberately cheap and auditable rather than accurate on adversarial titles, matching the rest of the codebase's approach to classification.
- Intent consistency across a SERP uses a 60 percent majority threshold. Below that, no single class dominates and the SERP is treated as mixed, which the core spec says makes deliberate targeting unreliable regardless of content quality.
- The five commercial filters in can-i-actually-rank are implemented as skill-level judgment against `context/business.md` prose, not as a pure function. Unlike the SERP verdict itself (deterministic, code-tested), ICP match and product fit require reading prose a human wrote, which is exactly the judgment layer's job and not the deterministic core's.
- The blueprint CLI assembles one node per cluster as a first-pass tree (single level, parented at root). Full hierarchical parenting, category-node promotion and depth-ceiling enforcement are specified in spec/site-blueprint.md and performed by the map-my-site skill's judgment over the deterministic primitives; the code guarantees the things that must not be left to judgment: collision detection, the permutation substance gate, and the authority budget. This mirrors the split already established between can-i-actually-rank (code verdict engine, skill-level commercial filters).
- estimateIndexedRate treats any GSC page with nonzero impressions as indexed, since no publish-date history exists yet to compute a true cohort-based indexation rate. This is stated as a proxy in the code comment; a future block should track publish dates per node once blueprint status transitions are recorded in the ledger.
- The legacy lazarus-pit files (analyze/findings.ts, analyze/component-mapper.ts, fetch-clarity.ts, run.ts) were removed rather than kept as dead code. They defined a second, incompatible Finding type from a UX-friction era of this project and were unused by every current command path except the old issues/filer.ts, which is now rewritten against src/analyze/checks.ts's Finding.
- Issue titles never embed the live metric value (e.g. a link count or a position). A value that changes every run would make title-based dedupe treat the same finding as new each time, which is the exact duplicate-filing failure this lineage already fixed once as lazarus-pit. Titles are keyed on check plus URL plus tier only.
- shipped is appended from a commit trailer only when the finding's current ledger status is acknowledged or in_progress. A finding still in opened that starts passing goes straight to closed on re-measure; nobody claimed to fix it, so there is nothing to verify, and appending shipped there would open a verification window on a claim nobody made.
- routine persists the last-seen commit ref in data/.last-routine-ref so shipped detection scans only new commits on each run, keeping repeated runs idempotent without rescanning full history.
- renderReport's spine has no "What did nothing" section by design. That belongs to what-actually-worked, which reuses didNothing() from src/ledger/query.ts directly rather than this module restating the same logic, per the redundancy rule in spec/false-positives.md section 5.
- planCompaction operates purely on snapshot references (name, fetched_at) and never touches data/ledger.jsonl. The ledger is permanent regardless of snapshot age; only the raw crawl/gsc/ga4 snapshot directories older than 90 days are downsampled to one per ISO week.
- checkWindowAvailability computes availability from the earliest snapshot's own fetched_at rather than a config value, so the refusal date is always grounded in what actually happened on this site, not a fixed assumption about onboarding date.
